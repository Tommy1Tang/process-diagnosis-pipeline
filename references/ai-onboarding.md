# AI 上岗：从断点到判定（D 轨道）

**这是 D 轨道，不是第七阶段。** 它吃断点清单，吐判定和规则；诊断的活仍归六阶段。

**入口**：手上已有一条或几条断点（来自阶段 3，也可以客户直接给）。
**出口**：判定卡（能不能交给 AI）+ 规则卡（交给 AI 之后怎么写）。
**不做**：不重复画现状、不重复找断点、不重复定指标。缺这些，回阶段 2/3/5。

**核心判据**：一条断点能不能交给 AI，只取决于它**能不能被写成可判定的条件**。
能说出"看到什么信息 → 做什么决定"，才是可判定的。说不出的，一律不是 AI 的活。

## D-① AI 适配判定（五问否决制）

### 第 0 步：先筛断点类型

| 断点类型 | 能不能进 D-① | 该谁解 |
|---|---|---|
| **说不清**（责任/口径/标准模糊） | ✅ **只有这一类进来** | 写成可判定条件 → AI |
| 多余 | ⛔ 不进 | 删掉（六动作第 1 步） |
| 缺失 | ⛔ 不进 | 补流程 |
| 顺序错 | ⛔ 不进 | 重排/并行 |
| 指错 | ⛔ 不进 | 修指标/权限 |

> 十有八九，客户的流程问题不在这条线上。**能说"这条不该上 AI"，是这个工具最常用的功能。**

### 五问：任一不过即否

| 顺序 | 问题 | 判据 | 答"否"时的动作 |
|---|---|---|---|
| ① 这活该不该存在 | 去掉这一步，流程还跑得通吗？客户损失什么？ | 跑得通、损失说不清 → **停**。这是"多余"，归消除，不是自动化 | 回六动作第 1 步，删 |
| ② 量够吗 | 每周发生几次？单次多久？ | 每周 < 5 次 或 单次 < 10 分钟 → 不值得。观察期攒不出数据，ROI 算不过来 | 不做，或并入相邻判断 |
| ③ 能写成条件吗 | **两个现在做这事的人，会不会做出同样的判断？** | 不会 → 口径没统一。先统一口径，不是上 AI | 回阶段 4「消除」，统一口径后再来 |
| ④ 判断要素拿得到吗 | 需要读的数据在哪个系统？谁授权？ | 拿不到 → 是数据集成问题，不是 AI 问题 | 先解数据接入 |
| ⑤ 错了能撤吗 | 最坏结果是什么？能补救吗？多久能发现？ | 不能撤（付款/合同/合规判定）→ **只能出建议，不能执行** | 降级为"建议模式" |

**③ 是五问里最狠的一问。** 它用"两个做事的人会不会一致"来检测口径是否统一——比问"你们有标准吗"准得多，因为没人会承认自己没标准。

### 五种结论

| 结论 | 条件 | 下一步 |
|---|---|---|
| ✅ **可执行**（auto） | 五问全过，⑤可撤 | 写规则卡，先进 observe |
| ⚠️ **可建议**（人确认） | ①–④ 过，⑤不可撤 | 写规则卡，永久停在"建议 + 人确认" |
| 🔧 **需先改造** | ③ 或 ④ 不过 | 回阶段 4：统一口径 / 补数据 |
| ⛔ **不该上**（多余） | ① 不过 | 回六动作第 1 步：删 |
| ⛔ **不该上**（类型不对） | 第 0 步就被筛掉 | 按对应类型处理 |

### 快速三问（客户会上当场用，1 分钟）

1. **这活每周做几次？** < 5 次 → 不用上。
2. **两个人做会不会做出同样的判断？** 不会 → 先统一口径。
3. **判错了能不能改回来？** 不能 → 只能出建议，不能自动执行。

三问就是一票否决。答不上任何一条，就是"现在不能上"。

### 门禁（不过不许往下）

- [ ] 五个问题都有明确答案，没有"大概/应该/看情况"
- [ ] 判"可执行"时，能当场写出一条具体条件句：「如果 A 且 B，则 C」
- [ ] 判"可执行"时，写下最坏结果 + 撤回动作 + 谁执行撤回
- [ ] 断点原文和客户原话已记录（判定不能脱离原话）

### 反模式

| 说法 | 问题 |
|---|---|
| "这个用 AI 肯定能行" | 说不出条件句 = 没判定 |
| "先上了再调" | 没有判定就放权，等于拿客户生产环境做实验 |
| "客户要求上 AI" | 需求不是适配。客户要的常常是"少加班"，不是"要 AI" |
| "同行都上了" | 不是判据。同行上的可能是另一类断点 |
| "先做个 Demo 看看" | Demo 只能证明能跑，不能证明判得对 |

## D-② 准入规则写法

**规则定义**：一条规则 = 一个判断单元 = 一张卡。
**判据**：一个没参与项目的人，只拿这张卡，能不能做出和你一样的判断？不能，就是规则写得不够硬。

### 一、从"不接什么"开始写

先写排除项，再写纳入项。理由：人对"什么不能干"比"什么能干"清楚得多，而规则写坏 90% 是写得太宽。

顺序：**不接的三类 → 必接的两类 → 其余转人工 → 边界情况**。

### 二、规则卡九字段

| 字段 | 写什么 | 缺了会怎样 |
|---|---|---|
| 名称 | 一句话说清它判什么 | 后面没法引用 |
| 触发面 | 哪些通道/哪些消息会进来 | 规则不知道对谁生效 |
| 判定条件 | 「如果 A 且 B 且 C」——必须是可观察的事实 | 变成靠模型感觉 |
| 输出动作 | 「则做 D」（建单/答复/打标/转人） | 判了不落地 |
| 不满足时 | 转给谁、用什么方式 | 消息掉进黑洞 |
| 不接的边界 | 明确排除的类型 | 规则太宽，什么都接 |
| 依据 | 谁说的、哪份文件、哪次访谈 | 客户换人后无法追溯 |
| 反例 | 什么情况下这条会判错 | 观察期无法校准 |
| 版本/观察期 | 第几版、什么时候放的权 | 出问题无法回滚定位 |

### 三、三类反例（每条规则交出去前，对照一遍）

#### A. 太宽——写了等于没写

| 反例 | 错在哪 | 怎么改 |
|---|---|---|
| 「客户在群里提问，判断是否需要技术介入，需要则建单」 | 没定义"技术介入"。价格、合同、投诉都算"需要介入" | 列出不接的三类（价格/合同/投诉），或列出必接的两类（含报错截图、含版本号） |
| 「消息提到产品就归类为产品问题」 | 竞品对比、招聘帖、行业新闻也会提到产品名 | 加两个限定：发送者是已购客户 **且** 含具体异常描述 |
| 「超过 3 天未回复的工单自动催办」 | 客户在等我方内部时，催办是打扰；节假日重复催 | 加「等待方 = 客户」和「非节假日」两个条件 |

#### B. 太窄——写了也等于没写

| 反例 | 错在哪 | 怎么改 |
|---|---|---|
| 「同时含订单号 + 型号 + 故障码 + 期望日期才建单」 | 真实消息很少这么全，一个月接 2 单，白建 | 必填降到 1 个（订单号 **或** 客户名），缺项改为"追问"而不是"不接" |
| 「仅处理 VIP 客户的技术问题」 | VIP 量少，观察期攒不出样本；且"VIP"本身没定义 | 先全量 observe，看 VIP 与非 VIP 的判断差异，再决定要不要分 |
| 「只处理工作日上午 9–18 点」 | 把时间当权限，掩盖了"非工作时间谁兜底"的真问题 | 时间限制属于**转人工策略**，不属于准入规则，移到"不满足时"栏 |

#### C. 太模糊——模型每次判得不一样

| 反例 | 错在哪 | 怎么改 |
|---|---|---|
| 「判断客户情绪，激烈则升级」 | "激烈"不可判定，每次标准不同 | 换成可观察信号：含"投诉/退款/律师/曝光"等词，**或** 同一客户 24h 内第三次提同一问题 |
| 「如果问题比较严重，转主管」 | "严重"是主观词 | 给阈值：涉及金额 > X **或** 影响客户数 > Y |
| 「参考历史类似工单的处理方式」 | 没定义"类似"，没说参考几条，冲突听谁的 | 「取最近 5 条同产品、同故障类型的已结案工单，结论一致则采纳，不一致转人工」 |

### 四、三条自检（交规则前必做）

1. **十单测试**：拿最近 10 条真实消息过一遍。接 0 条 = 太窄；接 10 条 = 太宽；接 3–7 条 = 合理。
2. **新人测试**：找一个没参与项目的人，只给卡片。他判的和你一样吗？不一样 = 太模糊。
3. **最坏结果测试**：这条规则判错时，最坏结果是什么？能撤回吗？不能撤回 = 不许开 auto。

### 门禁（不过不许交）

- [ ] 每条规则都有至少一条反例（"什么情况下会判错"）
- [ ] 每条规则都写了"不满足时转给谁"（否则消息掉黑洞）
- [ ] 第一轮开 auto 的规则 **≤ 1 条**
- [ ] 每条规则都能通过十单测试（接 3–7 条之间）
- [ ] 规则的"依据"能追到具体的人、具体的访谈、具体的文件

### 反模式

| 说法 | 问题 |
|---|---|
| "规则写得越细越好" | 太细 = 永不触发 = 等于没写。第一轮窄一点，但别窄到零 |
| "让模型自己判断就行" | 那不是准入规则，是放任。规则的作用是给出**边界**，模型在边界内判断 |
| "先写 20 条再上线" | 第一轮 3 条封顶。规则多了，误判了不知道是哪条的问题 |
| "规则写完就不用改了" | 规则会漂。业务变了、口径变了，规则不改就会慢慢判错 |
| "客户说这样就行" | 客户的口头认可不是依据。要写下"谁说的、哪次、原话" |

## D-③ 放权：从 observe 到 auto

**定义**：放权 = 把"只记录"换成"真执行"。技术上 30 秒可逆，**沟通上不可逆**——客户记住的是那一次误判。

### 一、四档阶梯（不是二值）

| 档 | 叫什么 | 机器做什么 | 人做什么 | 适用 |
|---|---|---|---|---|
| **L0** | 影子 | 只记录"本来会做什么"，不执行、不通知 | 每周看一次记录 | 起点，必须 |
| **L1** | 建议 | 产出建议，推到人工队列 | 逐条确认后自己执行 | 高风险但高频的场景 |
| **L2** | 执行 + 通知 | 自动执行，同时告诉人"我做了 X，因为 Y" | 事后抽查 | **大多数场景该停在这** |
| **L3** | 执行 + 静默 | 自动执行，只写日志 | 每周看汇总 | 极低风险、极高频率 |

> 参考实现里 accept mode 只分 off/observe/auto 三档，L1/L2/L3 的差别靠**规则文本写"只建议"或"执行后通知"**来实现，不是靠开关。所以这三档是"写进规则的话"，不是"点一下的按钮"。

### 二、前置条件（五条，全过才放）

| # | 条件 | 阈值（起始值） | 不过时 |
|---|---|---|---|
| 1 | 观察时长 | ≥ 2 周，或 ≥ 3 个完整业务周期 | 继续 observe |
| 2 | 样本量 | ≥ 30 条判断记录 | 场景太低频，考虑放弃 |
| 3 | 准确率 | 它想接的里，人认为该接的 ≥ 80% | 改规则，不改场景 |
| 4 | 误判可归类 | 每条误判都能归到 D-④ 四类之一 | 说明规则太模糊，回 D-② |
| 5 | 规则已稳定 | 最近 7 天没改过规则 | 说明还没想清，继续 observe |

**阈值是起始值，不是标准。** 低频高价值场景（设备大修决策，一周两次但错一次几十万）该把第 2 条降到 10 条、第 3 条提到 95%。

### 三、放多少：规则 × 通道 × 人群

最容易犯的错是"整条规则全放"。实际可以在三个维度上各放一半：

| 维度 | 例子 |
|---|---|
| **规则** | 3 条规则里只放 R-01（最窄、最可逆的那条） |
| **通道** | 内部群放开，客户群不放开 |
| **人群** | 老客户放开，新客户不放开；工作时间放开，夜间转人工 |

**先放最窄的那一格，不是最宽的那一格。** 一个"只在内部群、只对老客户、只在工作时间"的 auto，比"全放"安全十倍，而且客户能接受。

### 四、怎么放：第一周到第四周

| 时间 | 做什么 | 看什么 |
|---|---|---|
| 放权前 1 天 | 写下退回路径 + 通知模板（不是出事再想） | 谁按退回键、多久内、怎么告知 |
| 第 1–3 天 | 每天看一次全部执行记录 | 有没有"它做了但我没预期"的动作 |
| 第 1 周末 | 给客户一份三行汇报（执行数/异常数/改了什么） | 客户的反应 |
| 第 2–4 周 | 每周看一次 | 误判是否集中在某一类 |
| 第 2 个月起 | 每周看 + 每月复盘一次 | 规则是否开始漂 |

### 五、退回机制（放权前必须写好）

| 项 | 必须写清 |
|---|---|
| **谁有权退回** | 你（技术回归）+ 客户责任人（业务叫停），两个人都能，不需要商量 |
| **多久内退回** | 发现严重误判 1 小时内；普通误判 24 小时内 |
| **怎么撤** | 规则切回 L0（30 秒）+ 撤回已执行的动作（撤消息/关单/改回） |
| **怎么通知** | 24 小时内一份简短说明：哪条判断错、为什么错、改了什么、下次怎么防 |
| **留什么证据** | 误判原文 + 判断依据 + 你的修正理由（这是下次放权的信用凭证） |

**退回不是失败，是流程的一部分。** 一次干净的退回 + 一份说明，比十次"没出事"更能建立信任——因为客户看到的是"出问题有人兜"。

### 六、三条不可放权红线（永不 auto）

| 红线 | 例子 | 为什么 |
|---|---|---|
| **不可撤回的动作** | 付款、合同签署、删除数据、发对外正式文件、锁定价格 | 撤回成本高于收益，且客户法务不认"AI 判错了" |
| **合规责任判断** | 合同条款、发票、税务、安全合规、资质审核 | 责任无法转移给工具 |
| **影响面不可控** | 群发、广播、批量修改、对外公告 | 一次错影响全部，且无法逐条撤回 |

红线是**预置否决**：不用每次判定，见到就停。它和 D-① 的第⑤问不同——⑤ 是"这条断点能不能执行"，红线是"这类动作永远不能自动"，跨项目生效。

### 七、降级触发（不用讨论，自动降）

| 触发 | 动作 |
|---|---|
| 一次严重误判（客户投诉 / 产生损失） | 立即切回 L0，当天写说明 |
| 一周内 3 次误判 | 切回 L0，改规则 |
| 依赖条件变了（数据源换、口径改、负责人离职） | 主动降级，别等出错 |
| 客户方换了对接人 | 主动降级到 L1，重新建立信任 |

最后一条最容易被忽略：**新对接人没有参与过 observe 期，他的信任额度是零。** 你不降级，他会用第一次误判来给你定性。

### 八、门禁（不过不许开 auto）

- [ ] 五条前置条件全过，且数字记在案（不是"感觉差不多了"）
- [ ] 退回路径写下来了：谁按、多久内、怎么撤、怎么通知
- [ ] 同时开 auto 的规则 ≤ 1 条
- [ ] 放权范围已限定到"规则 × 通道 × 人群"的最窄一格
- [ ] 监控节奏已排进日历（不是"我会看的"）
- [ ] 红线动作一条都没有（有就删掉规则，不是"小心一点"）

### 九、客户话术（三句，背下来）

1. **"我不是把控制权交出去，是把'只看'换成'做 + 每天复核'。"**
2. **"任何一条规则，我可以在 30 秒内收回，不影响已经做完的事。"**
3. **"如果它判错了，我 24 小时内告诉你哪条错了、为什么、改了什么。"**

第 3 句是关键——大多数乙方不敢承诺"主动告知误判"，而这恰恰是唯一能积累信任的动作。

### 十、反模式

| 说法 | 问题 |
|---|---|
| "跑了三天没出事，放开吧" | 三天不构成样本。没出事可能是没量，不是判得对 |
| "客户催上线，先放开" | 政治压力不是判据。放早了，第一次误判就终结项目 |
| "反正能撤回" | 撤回有沟通成本。撤三次，客户就不信这个工具了 |
| "同时放三条，效率高" | 出问题分不清是哪条。一次一条 |
| "放开后就不用管了" | 规则会漂。不管它，三个月后你会在客户投诉里知道它漂了 |
| "先全放，出问题再收" | 顺序反了。信任是攒出来的，不是试出来的 |
